# BE01 至 BE05 客户沟通准备说明

## 这部分工作解决了什么问题

我负责的是账号、家庭资料和管理员用户管理后端。BE01 至 BE05 已经把原来的简单页面连接到 Supabase，建立了注册、登录、资料管理、权限检查和管理员用户管理的完整基础流程。

这部分实现的核心结果是：普通家庭只能访问自己的账号和家庭资料，管理员只能在经过服务端角色验证后管理普通家庭账号，浏览器不能通过修改请求内容绕过这些限制。

## 面向客户的一分钟介绍

可以这样向客户说明：

> 我完成了平台的账号与权限后端。用户可以通过邮箱注册和登录，系统会验证账号初始化是否完整。登录后，用户只能查看和修改自己的家庭名称、家庭人数及隐私偏好。管理员区域使用独立的服务端权限检查，管理员可以创建、编辑、禁用、恢复和删除普通家庭账号，但不能任意修改密码或管理员角色，也不能查看其他家庭的原始资源使用记录。所有敏感管理员操作都只在服务器执行。

## BE01 注册与登录

### 实现的功能

- 使用 Supabase Auth 完成邮箱密码注册和登录。
- 用户密码由 Supabase Auth 管理，项目数据库不保存明文密码或密码副本。
- 注册密码必须至少 8 位，并包含大写字母、小写字母、数字和特殊字符。
- 注册页面支持 6 位邮箱验证码验证和重新发送确认邮件。
- 登录和注册错误转换为稳定、易理解的提示，不向用户显示 Supabase 内部错误。
- 使用 Next.js Proxy 验证和刷新 Cookie Session。
- 未登录用户不能直接访问需要登录的家庭页面。
- 修复了注册步骤切换时 React 输入框状态警告。

### 主要代码

- `src/features/auth/domain.ts`：密码规则和认证错误转换。
- `src/app/(public)/sign-up/page.tsx`：注册、验证码验证和重新发送邮件流程。
- `src/app/(public)/sign-in/page.tsx`：密码登录和成功跳转。
- `src/lib/supabase/proxy.ts`：Session 验证和刷新。
- `src/proxy.ts`：将 Session 检查接入 Next.js 请求流程。
- `src/app/(household)/layout.tsx`：登录后页面的服务端身份检查。
- `tests/auth.test.ts`：认证规则自动测试。

### 客户价值

- 平台不自行处理或保存用户密码，降低密码泄露风险。
- 未登录用户无法进入家庭功能区域。
- 用户收到的是安全、统一的错误信息，而不是技术堆栈。

## BE02 注册后账号初始化验证

### 实现的功能

- 新增 `GET /api/account/initialization`。
- 邮箱验证成功后检查新账号是否已经建立家庭资料和角色记录。
- 确认新账号角色为普通家庭，而不是管理员。
- 确认两个隐私开关默认关闭。
- 如果数据库初始化不完整，系统停止进入 Overview 并返回安全错误。
- 用户身份从经过验证的 Session 获取，不接受浏览器指定其他用户 ID。

### 主要代码

- `src/features/account/domain.ts`：初始化完整性判断规则。
- `src/features/account/server/initialization.ts`：服务端初始化查询。
- `src/app/api/account/initialization/route.ts`：初始化检查 API。
- `src/app/(public)/sign-up/page.tsx`：邮箱验证后调用初始化检查。
- `tests/account-initialization.test.ts`：缺失资料、错误角色和隐私默认值测试。

### 客户价值

- 避免用户注册成功但缺少必要资料，导致进入系统后功能异常。
- 防止注册用户通过客户端数据把自己设置为管理员。
- 隐私设置从账号建立时默认关闭。

## BE03 家庭资料 API

### 实现的功能

- 新增 `GET /api/profile`，读取当前用户自己的家庭资料。
- 新增 `PATCH /api/profile`，修改家庭名称、家庭人数和两个隐私偏好。
- 家庭名称限制为 1 至 60 个字符。
- 家庭人数限制为 1 至 20 的整数。
- 隐私字段必须是真正的 JSON boolean。
- 拒绝角色、所有者、系统假名和所有未知字段。
- Settings 页面不再直接操作数据库，而是通过受控 API 读写资料。
- API 使用用户 Session 和数据库 RLS 双重限制所有权。

### 主要代码

- `src/features/privacy/domain.ts`：Profile 字段白名单和输入验证。
- `src/features/privacy/server/service.ts`：本人资料读取和修改服务。
- `src/features/privacy/client.ts`：Settings 页面使用的 API 客户端。
- `src/app/api/profile/route.ts`：Profile GET 和 PATCH 路由。
- `src/features/privacy/settings.tsx`：连接真实 Profile API。
- `tests/profile.test.ts`：合法输入、边界值和越权字段测试。

### 客户价值

- 普通用户只能修改自己的家庭资料。
- 浏览器无法通过增加 `role` 或 `userId` 字段修改角色或其他家庭。
- 数据格式在进入数据库前经过服务端验证。

## BE04 管理员授权

### 实现的功能

- 建立共用服务端 `requireAdmin()`。
- 未登录用户访问管理员 API 时返回 HTTP 401。
- 普通家庭用户访问管理员 API 时返回 HTTP 403。
- 角色查询失败时返回安全错误，不继续执行管理员操作。
- Admin Users、Admin Challenges 和管理员页面布局使用同一套授权检查。
- 每个管理员 API 都在执行操作前重新验证 Session 和角色。

### 主要代码

- `src/features/admin/authorization.ts`：管理员授权结果规则。
- `src/features/admin/server/authorization.ts`：服务端 `requireAdmin()`。
- `src/app/(household)/admin/layout.tsx`：管理员页面访问检查。
- `src/features/admin-users/server/service.ts`：Admin Users 接入共用授权。
- `src/features/challenges/server/admin-service.ts`：Admin Challenges 接入共用授权。
- `tests/admin-authorization.test.ts`：401、403、角色查询失败和管理员通过测试。

### 客户价值

- 管理员按钮是否显示不再是唯一保护，真正的权限检查在服务器端执行。
- 普通用户即使手动构造管理员 API 请求，也会被拒绝。
- 管理员功能采用一套统一授权规则，减少不同接口出现权限漏洞的风险。

## BE05 管理员用户管理

### 实现的功能

- 管理员可以查看用户列表和必要的管理信息。
- 管理员可以创建普通家庭账号。
- 管理员创建的账号已确认邮箱，可以使用临时密码直接登录，不需要邮箱验证码。
- 管理员可以修改普通账号的邮箱、家庭名称和家庭人数。
- 管理员可以禁用和恢复普通账号。
- 管理员可以在明确确认后永久删除普通账号。
- 管理员不能通过该 API 修改用户密码或角色。
- 管理员不能禁用或删除管理员角色账号，也不能删除自己。
- 管理员不能通过用户管理功能查看其他家庭的水、电、垃圾原始记录。
- 所有高权限操作使用仅存在于服务器的 Supabase secret key。
- 服务端 secret 未配置时返回安全的 HTTP 503，而不是显示运行时堆栈。

### 主要代码

- `src/features/admin-users/domain.ts`：创建和更新用户的严格字段验证。
- `src/features/admin-users/server/service.ts`：列表、创建、修改、禁用、恢复和硬删除。
- `src/features/admin-users/client.ts`：管理员页面 API 客户端。
- `src/app/api/admin/users/route.ts`：用户列表和创建路由。
- `src/app/api/admin/users/[userId]/route.ts`：修改和删除路由。
- `src/app/(household)/admin/users/page.tsx`：管理员用户管理页面连接后端能力。
- `tests/admin-users.test.ts`：密码规则、允许字段和越界字段拒绝测试。

### 客户价值

- 管理员可以完成普通家庭账号的日常生命周期管理。
- 高权限密钥不会发送到浏览器。
- API 严格限制管理员可以修改的字段，避免权限范围无意扩大。

## 安全设计说明

- 密码由 Supabase Auth 管理，应用不保存或返回密码。
- 普通浏览器代码只使用 publishable key。
- secret key 只用于服务端管理员代码，不能使用 `NEXT_PUBLIC_` 前缀。
- 用户身份来自验证后的 Session，不信任浏览器提交的用户 ID。
- 普通家庭资料同时受到 API 所有权检查和数据库 RLS 保护。
- 管理员 API 每次请求都重新检查角色。
- API 拒绝未批准字段，不会因为 TypeScript 类型而信任外部 JSON。
- 敏感响应设置 `Cache-Control: no-store`。
- 错误响应不包含数据库详情、密钥或内部堆栈。

## 客户沟通时需要主动说明的限制

### 注册确认邮件模板

当前 Supabase 确认邮件发送确认链接，而注册页面设计为输入 6 位验证码。代码已支持验证码，但 Supabase 后台维护者仍需把邮件模板改为显示 `{{ .Token }}`。在模板修改完成前，不应向客户演示验证码邮件流程。

### 删除方式

当前版本按照已确认决定使用永久硬删除。Week 8 后续讨论中提出过可恢复的软删除，但数据库目前没有提供相应字段和权限规则。如果客户要求误删恢复，需要把软删除作为后续改进，不应声称当前版本可以恢复已删除账号。

### BE06 尚未实施

BE06 的完整账号与权限错误处理仍是下一项任务。BE04 已经覆盖基础的 401 和 403，BE05 已经实现禁用与恢复，但停用账号在页面、Session 和各受保护 API 中的完整行为仍需要在 BE06 继续统一和测试。

## 客户可能提出的问题

### 你们是否保存用户密码

不保存。密码由 Supabase Auth 管理，业务数据库没有密码字段。

### 普通用户能否把自己改成管理员

不能。Profile API 拒绝角色字段，数据库也不允许普通用户修改 `account_roles`。

### 管理员能否查看所有家庭的水电垃圾记录

不能。用户管理权限只包括账号和必要的家庭管理信息，不包含其他家庭的原始资源数据。

### 管理员能否修改用户密码

当前版本不能。这是明确的权限边界，BE05 没有提供任意密码修改接口。

### 被删除的账号能否恢复

当前版本不能。删除采用硬删除，并在页面操作前明确提示不可恢复。

### 为什么管理员创建的用户不需要邮箱验证码

这是当前确认的业务规则。管理员通过受保护的服务端接口创建账号，系统将邮箱标记为已确认，使账号可以立即使用临时密码登录。

### 如果有人手动调用管理员 API 会怎样

服务端会验证有效 Session，并查询数据库角色。未登录返回 401，非管理员返回 403，不会仅依赖页面上的按钮是否可见。
